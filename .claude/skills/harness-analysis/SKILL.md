# harness-analysis: harness 源码分析方法论

本 skill 沉淀自对 vendored Claude Code 源码的逐层分析(query loop / 工具权限 / 上下文治理 / skills / 错误恢复), 方法在 01-03.9 全部章节中验证过。

## 分析流程(四步循环)

```
1. zoom-out 先行
   模块在系统里的角色(一句话) → 上下游(进什么/出什么) → 才钻内部细节
   触发: 打开不熟悉的文件时; 已知精确位置的定向修改不触发

2. 论断 → 验证 → 增量
   有外部论断(书/文章/架构图)时: 先复述论断 → 逐条对源码验证
   (标 file:line) → 重点产出【论断没讲的增量】
   增量的高发区: 顺序依赖的因果注释 / 防御性分层 / 事故记录注释

3. 证据规则
   - 注释即证据: 引用原文(英文原文 + 中文释义), 不转述
   - 事故注释是金矿: "burned last quarter" / "烧数千次 API" /
     "10.2% of fleet cache_creation" 这类数字与事故, 必须保留
   - 拿不到实现时诚实标注: "实现被剥离, 机制从调用侧注释还原"

4. 文档化(分析即沉淀)
   结构: 源码细节(行号锚定) → 总表(解决什么/怎么做/代价)
        → 机制展开 → 总纲(一句话收敛)
```

## DCE 剥离区的处理(外部构建源码必读)

若源码来自 source maps 恢复(external 构建), `feature('X')` 守卫的模块被物理剥除(stub)。应对:

- 调用侧完整(调用点在守卫外), 注释也完整(DCE 剥代码不剥注释)
- 从**调用契约 + 参数 + 注释**还原行为语义, 标注"vendored stub"
- 典型剥离区: 实验性 feature gate 的实现体(snip/collapse/skill search)

## 七部件 checklist(分析一个 harness 是否完整)

| 部件 | 核心问题 |
|---|---|
| prompt 控制面 | 静态/动态如何分界? 缓存如何不被配置组合碎片化? |
| query loop | 状态怎么跨迭代携带? 治理在模型调用前还是后? |
| 工具系统 | 工具如何声明风险? 调度如何保证因果秩序? |
| 权限 | 三态(allow/deny/ask)? 多 agent 下 ask 寻址到谁? |
| 上下文治理 | 各手段的粒度/破坏性/缓存代价? 预算数字? |
| 错误恢复 | 恢复是否分层且单发? 死循环防护在哪层? |
| 中断/补账 | 每个 tool_use 是否必有配对结果? |

## 贯穿性判据(快速评估设计质量)

- 上下文形态稳定性: 会变的东西是否都隔离在缓存前缀之外?
- 重试是否被管理: 保护位逐站判定, 而非全局重试上限
- 成本决定通道: 秒级操作是否藏在主路径的空闲里?
- 账本闭环: 执行可作废, 结果必须补齐(synthetic)
- 防御性分层: 最便宜的一层(纯筛选)放最外面兜底

## 文档格式规范(本仓库沿用)

- 编号: 普通数字(1. / 2.), 不用带圈字符
- 术语: 首次出现给"术语: X"小节(定义 + 源码开关 + 对照)
- 图: ASCII 优先(结构/时序/对比), 表格承载"解决什么/怎么做/代价"
- 引用: 站内相对链接, 带 §N 前缀(如 `[§3 受控重启](03.5-context.md)`)
- 每个 prompt/指令段: English 纯原文块 + 中文纯翻译块, 评述移块外
- 原则: 长段文字超一个要点时, 先转列表或图
